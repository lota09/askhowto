# RAG 개념 정리: 문서를 다 넣기, RAG, 도구로 읽게 하기

도우미 봇에 위키 같은 자료를 붙일 방법을 정하기 전에 개념부터 맞춰 둔다.
예시는 모두 이 봇(askhowto)과 선릿 밸리 위키 기준이다.

## 1. 전제: LLM은 입력으로 받은 글만 본다

- LLM은 학습 때 본 지식과, **이번 요청에 넣어 준 글(컨텍스트)**만으로 답한다. 서버 파일이나 위키를 스스로 열어 보지 못한다.
- 한 번에 넣을 수 있는 양에는 상한(컨텍스트 창)이 있다.
  - 로컬 Gemma: 약 3,200토큰
  - NIM glm, Gemini: 수십만~100만 토큰
- 넣는 양이 많을수록 **느리고 비싸고**, 중간에 묻힌 내용을 놓치기 쉽다("lost in the middle").
- 그래서 "무엇을 넣을지 고르는 일"이 답의 질을 정한다. 아래 세 방식은 모두 **고르는 방법**이 다를 뿐이다.

## 2. RAG(검색 증강 생성)의 원리

RAG = **R**etrieval(검색) + **A**ugmented(덧붙여) + **G**eneration(생성).
답을 만들기 전에 **프로그램이 먼저 관련 자료를 찾아** 질문 앞에 붙여 주는 방식이다.

```
[미리 한 번]  자료 ──잘게 나눔(청크)──▶ 색인 (어떤 말이 어느 조각에 있는지)
[질문마다]    질문 ──검색──▶ 관련 조각 몇 개 ──프롬프트에 붙임──▶ LLM ──▶ 답
```

이 봇이 지금 하는 일이 정확히 이것이다.
1. **색인 (`python3 -m askhowto build`):** 퀘스트·농업연감·상점·레시피 등을 조각 1,631개로 나누고, 한글 두 글자 단위로 색인한다(BM25).
2. **검색 (질문마다):**
   - 질문에 나온 아이템·NPC 이름은 사전으로 찾아 해당 조각을 반드시 넣는다(확정 정보).
   - 나머지는 BM25 점수 순으로 고른다.
3. **생성:** 고른 조각(클라우드 모델은 12,000자, 로컬은 4,000자)을 질문 앞에 붙여 LLM에게 보낸다.

핵심은 **무엇을 넣을지 LLM이 아니라 검색 프로그램이 정한다**는 점이다. LLM은 받은 것만 보고 답한다.

## 3. 세 가지 방식 비교

| | ① 문서를 통째로 넣기 | ② RAG (지금 방식) | ③ 도구를 쥐어주기 (에이전트형) |
|---|---|---|---|
| 무엇을 볼지 누가 정하나 | 정하지 않음 (전부) | 검색 프로그램 (질문 받기 전에 규칙으로) | LLM 자신 (읽으면서 판단) |
| LLM 호출 횟수 | 1번 | 1번 | 2~4번 (도구 쓸 때마다 왕복) |
| 질문당 입력량 | 위키만 약 24만 토큰* | 약 2,200토큰 (실측) | 처음 + 도구 결과만큼 (보통 수천 토큰) |
| 응답 시간 | 매우 김 | 5~10초 | 왕복마다 5~10초 추가 |
| 주된 실패 | 느림·비쌈, 묻힌 내용 놓침, 무료 한도 금방 소진 | 검색이 엉뚱한 조각을 고르면 답도 틀림 | 모델이 검색을 안 하고 추측, 엉뚱한 검색어, 도구 호출 형식 실수 |
| 필요한 모델 수준 | 긴 문맥을 다루는 큰 모델 | 작은 모델도 됨 (Gemma로 운영 중) | 도구 호출을 잘하는 큰 모델 (Gemma는 어려움) |

\* 위키 원문(위키 문법 포함) 95만 자 ÷ 약 4자/토큰. 'Sell Values'와 'Longwings' 두 표만 48만 자다.

- **①**은 자료가 작을 때(수천 토큰)만 현실적이다. 위키 전체를 질문마다 넣으면 NIM 무료 한도와 응답 시간을 감당할 수 없다. 로컬 Gemma에는 아예 안 들어간다.
- **②**는 빠르고 싸지만 **처음 고른 것이 전부**다. 첫 검색이 놓치면 LLM은 그 사실조차 모른다.
- **③**은 LLM이 "부족하다"고 느끼면 더 찾아볼 수 있다. 대신 느리고, 모델이 도구를 제대로 쓴다는 보장이 없다.
- 실제로는 **②로 먼저 넣고, 부족할 때만 ③으로 더 찾게 하는 혼합형**이 흔하다.

## 4. "RAG 도구"와 "문서 읽기 도구"는 어떻게 다른가

둘 다 LLM에게 쥐어주는 도구지만, **LLM이 무엇을 알아야 쓸 수 있는지**가 다르다.

| | 문서 읽기 도구 | RAG(검색) 도구 |
|---|---|---|
| 입력 | **주소**: 문서 이름 + 위치(줄 범위, 섹션) | **질문·검색어**: "로터스 열매 얻는 법" |
| 출력 | 그 위치의 내용 그대로 | 관련 있어 보이는 조각 몇 개 (점수순) |
| 어디를 볼지 아는 쪽 | **LLM이 이미 알아야 함** | **도구(색인)가 찾아 줌** |
| 비유 | 책의 "37쪽 펴기" | 책 뒤의 "찾아보기(색인)" |

**문서 읽기 도구만으로는 부족하다.**
- 어느 문서의 어디를 읽을지 모르면 처음부터 순서대로 넘겨 볼 수밖에 없다.
- 그러면 결국 ①(전부 읽기)을 여러 번에 나눠 하는 셈이 되고, 왕복 수만큼 더 느려진다.

**읽기 도구가 쓸모 있으려면 "어디를 볼지" 알려 줄 것이 함께 있어야 한다.**
- **목록·목차 도구:** 문서 제목 목록, 문서 안의 섹션 제목. 사람이 목차를 보고 펼치는 방식이다.
- **검색 도구:** 질문을 주면 문서 이름과 위치를 알려 준다. 이 검색 도구 안에서 돌아가는 것이 바로 2장의 RAG 색인(BM25나 임베딩)이다.
  즉 **"RAG 도구" = RAG의 검색 단계를 LLM이 원할 때 부를 수 있게 도구로 꺼내 놓은 것**이다.

### 이 세션(Claude Code)이 큰 문서를 일부만 읽는 방식

제가 큰 파일을 전부 읽지 않는 것은 **검색 도구와 읽기 도구를 함께 쓰기** 때문이다. 이번 세션에서 실제로 한 일:

1. `grep -n 'def \|^[A-Z_]* = ' rag.py` → 함수와 상수가 몇 번째 줄에 있는지 찾는다. **검색 도구 역할.**
2. `Read rag.py offset=56 limit=192` → 그 범위만 읽는다. **읽기 도구 역할.**
3. 위치를 이미 알 때(방금 수정한 함수, README의 `## 설치` 섹션)는 1번을 건너뛰고 바로 범위를 읽는다. **목차를 아는 경우.**

다만 제가 쓰는 검색(grep)은 **글자가 그대로 같은 것**만 찾는다. 코드에서는 함수 이름이 정확하니 잘 맞지만, 사람 말로 된 질문에는 그대로 쓰기 어렵다.

- "썩은살점 구하는 법" → 문서에는 "썩은 살점", "Rotten Flesh", "'부패' 슬라임의 플로트"로 적혀 있다.
- 그래서 봇의 검색은 조사를 떼고, 두 글자 단위로 비교하고, 이름 사전으로 영어 이름과 오타까지 맞춘다.

생각하신 "문서 읽기 도구"를 이 봇에 옮기면 다음 세 가지 세트가 된다.
- `list_pages()`: 위키 문서 제목 목록
- `search_docs(검색어)`: 관련 문서와 섹션 위치. 내부는 RAG 색인
- `read_page(제목, 섹션)`: 그 부분만 읽기

## 5. 도구를 쓰면 한국어 번역이 필요 없지 않을까?

**읽고 답하는 단계에서는 맞다.**
- NIM glm이나 Gemini 같은 큰 모델은 영어 위키를 읽고 한국어로 답할 수 있다.
- 필요한 부분만 읽으므로 문서 전체를 미리 번역해 둘 이유가 줄어든다.

**문제는 "찾는" 단계다.** 플레이어는 한국어로, 그것도 이 팩의 한국어 번역명으로 묻는다.
- BM25 같은 낱말 검색은 언어가 다르면 아예 걸리지 않는다. "캐롤라인"과 "Caroline"은 겹치는 글자가 없다.
- LLM이 영어 검색어로 바꿔 검색할 수는 있다. 하지만 바닐라 아이템("썩은 살점" = Rotten Flesh)과 달리, **팩 고유 번역명은 모델이 모른다.** 예를 들어 '플로트 리핏'이 Plort Rippit인지 짐작밖에 못 한다.

그래서 번역 대신 필요한 것은 **한↔영 다리**다. 이 봇은 이미 그 다리를 갖고 있다.
- 이름 사전 `data/names.jsonl`: 아이템·블록·몹 약 1만 9천 개의 한국어·영어 이름
- 위키 문서 제목은 대부분 아이템·NPC의 영어 이름이다(Caroline, Fish Pond, Ancient Cog …).
- 질문의 "캐롤라인"을 사전으로 "Caroline"으로 바꾸면 위키 "Caroline" 문서를 **번역 없이** 바로 찾는다.
  ②(첫 검색에 확정 정보로 넣기)와 ③(검색 도구 안에서 한국어 검색어를 영어로 바꾸기) 모두에 쓸 수 있다.
- 다리가 끊기는 경우(이름이 아닌 개념어: "초반에 뭐부터 해?" ↔ "Getting Started")는 다른 방법이 필요하다.
  - 다국어 임베딩 검색: 뜻으로 찾음, NIM에 임베딩 모델이 있음
  - 개념어 몇 개의 영어 대응어

**미리 번역하는 게 여전히 의미 있는 경우**
- **로컬 Gemma로 폴백될 때:** 작은 모델은 도구를 못 쓰고, 영어 문서를 읽고 한국어로 정확히 답하는 것도 약하다.
- **도구 없이 ②만으로 답하는 질문:** 첫 검색에 위키 내용을 한국어 조각으로 넣고 싶을 때.
- **왕복을 줄여 빠르게 답하고 싶을 때:** 도구는 왕복마다 5~10초가 더 든다.

**정리하면**
- **이름 다리(사전) + 영어 원문 + 큰 모델**이면 번역 없이 된다. 첫 검색에서 영어 원문 조각을 넣고, 부족하면 도구로 더 읽는다.
- 번역은 "로컬 폴백에서도 위키 지식을 쓰고 싶은가", "개념어 질문을 얼마나 잘 찾아야 하는가"에 따라 고를 **선택 사항**이다.
- 어느 쪽이 나은지는 같은 89문항 평가에 위키 관련 질문을 더해 두 방식을 비교하면 확인할 수 있다.

## 6. 이 봇에 적용하면

| 구성 | 하는 일 | 상태 |
|---|---|---|
| 첫 검색 (②) | 이름 사전 + BM25로 서버 자료를 넣는다. 위키는 이름 다리로 영어 원문 조각을 함께 넣을 수 있다 | 운영 중 (위키는 아직 없음) |
| 검색 도구 (③) | 부족할 때 LLM이 `search_docs`를 부른다. 한국어 검색어는 사전으로 영어도 같이 찾는다 | 계획 |
| 읽기 도구 (③) | `read_page(제목, 섹션)`로 검색이 알려 준 부분만 읽는다 | 계획 |
| 로컬 폴백 | 도구 없이 ②만 쓴다. 문맥 4,000자 | 운영 중 |
